# مشخصات: نوع ثبت‌نام، نوع پرداخت، و قرارداد مدرسه‌ای

سند نیازمندی‌ها بر اساس توافق محصول (بدون جزئیات پیاده‌سازی کد).  
هدف: تفکیک مفاهیم UI/دامنه و افزودن قرارداد مدرسه بدون ساختن رکورد دانش‌آموز فردی.

---

## ۱) خلاصه تغییرات

1. فیلد فعلی «نوع ثبت‌نام» که در واقع منطق **صورتحساب/پرداخت** است (`SINGLE_SESSION` / `MONTHLY` / `SCHOOL_ENROLLMENT`) از عنوان «نوع ثبت‌نام» جدا شود و با عنوان **«نوع پرداخت»** نگه داشته شود (همان مقادیر).
2. فیلد جدید **«نوع ثبت‌نام»** اضافه شود با دو مقدار: **خصوصی** و **مدرسه‌ای**.
3. برای **مدرسه‌ای**: نام مدرسه + تعداد دانش‌آموز + مبلغ واحد؛ مبلغ کل فقط نمایش؛ **بدون ساخت Student جدید**.
4. پرداخت‌های قرارداد مدرسه: اقساط آزاد در ماه‌های مختلف؛ در لیست پرداخت‌ها مبلغ کل + معادل سرانه (`مبلغ ÷ تعداد`).
5. فعلاً فقط دریافت پول (بدون کمیسیون مشاور/حقوق برای قرارداد مدرسه).
6. ویرایش قرارداد (تعداد / مبلغ واحد / نام و …) و محاسبه مجدد مبلغ کل و مانده مجاز است.

---

## ۲) تفکیک فیلدها در فرم دانش‌آموزان

فرم ثبت/ویرایش در صفحه دانش‌آموزان باید دو مفهوم جدا داشته باشد:

### ۲.۱ نوع ثبت‌نام (جدید) — `registration_channel`

| مقدار | معنی |
|--------|------|
| `PRIVATE` (خصوصی) | ثبت‌نام فردی |
| `SCHOOL` (مدرسه‌ای) | قرارداد با مدرسه؛ بدون ساخت دانش‌آموز فردی |

**خصوصی — فیلدهای وابسته (طبق توافق قبلی):**

- نحوه برگزاری: `ONLINE` (آنلاین) | `IN_PERSON` (حضوری) — اجباری وقتی نوع = خصوصی

**مدرسه‌ای — فیلدهای وابسته:**

- نام مدرسه (اجباری)
- تعداد دانش‌آموزان (اجباری، عدد صحیح > 0)
- مبلغ به ازای هر دانش‌آموز (اجباری)
- مبلغ کل قرارداد = `تعداد × مبلغ واحد` — **فقط نمایش** (محاسبه در UI؛ بک‌اند هم هنگام ذخیره تأیید/ذخیره کند)

### ۲.۲ نوع پرداخت (قبلی با عنوان جدید) — `enrollment_billing_mode`

همان مقادیر فعلی سیستم، فقط عنوان UI عوض شود:

| مقدار | برچسب پیشنهادی UI |
|--------|-------------------|
| `SINGLE_SESSION` | تک‌جلسه‌ای — یک پرداخت |
| `MONTHLY` | ماهانه — هر پرداخت = یک ماه |
| `SCHOOL_ENROLLMENT` | سالانه — قرارداد با اقساط |

> توجه: مقدار `SCHOOL_ENROLLMENT` در سیستم فعلی به معنی «صورتحساب سالانه یک دانش‌آموز با اقساط» است و با «نوع ثبت‌نام = مدرسه‌ای» یکی نیست. نوع ثبت‌نام مدرسه‌ای موجودیت قرارداد مدرسه است؛ نوع پرداخت می‌تواند جداگانه روی جریان فردی باقی بماند یا برای قرارداد مدرسه محدود/مخفی شود (در پیاده‌سازی مشخص شود).

### ۲.۳ رفتار فرم وقتی نوع ثبت‌نام = مدرسه‌ای

- **هیچ رکورد `Student` جدیدی ساخته نشود.**
- به‌جای آن یک **قرارداد مدرسه** (`SchoolContract`) ذخیره شود.
- در UI می‌توان همان مودال/فرم دانش‌آموزان را با شاخه شرطی استفاده کرد، یا پس از انتخاب «مدرسه‌ای» فیلدهای فردی (نام/نام خانوادگی دانش‌آموز و …) مخفی و فیلدهای قرارداد نشان داده شوند.
- در لیست/نمای مرتبط نشان داده شود که این مدرسه چند دانش‌آموز ثبت کرده (فیلد `student_count`)، نه ۴۰ ردیف دانش‌آموز.

### ۲.۴ رفتار فرم وقتی نوع ثبت‌نام = خصوصی

- همان جریان فعلی ساخت/ویرایش `Student`.
- فیلد نحوه برگزاری (آنلاین/حضوری) اجباری.
- فیلد «نوع پرداخت» با مقادیر فعلی نمایش داده شود.
- نام مدرسه برای خصوصی اختیاری است (یا مخفی، طبق تصمیم UI نهایی).

## ۳) موجودیت قرارداد مدرسه

### ۳.۱ فیلدهای اصلی

| فیلد | توضیح |
|------|--------|
| `school_name` | مثلاً شهید بهشتی |
| `student_count` | تعداد دانش‌آموزان قرارداد (مثلاً ۴۰) |
| `unit_price_cents` | مبلغ به ازای هر دانش‌آموز |
| `total_amount_cents` | `student_count × unit_price_cents` (ذخیره یا همیشه مشتق؛ ترجیح: ذخیره + اعتبارسنجی سمت سرور) |
| وضعیت / تاریخ شروع / توضیحات | در صورت نیاز |
| سازمان و … | هم‌راستا با بقیه دامنه در صورت وجود |

**ساختن Student برای هر نفر لازم نیست.**

### ۳.۲ ویرایش

- ویرایش نام مدرسه، تعداد، مبلغ واحد و … مجاز است.
- پس از تغییر تعداد یا مبلغ واحد:
  - `total_amount_cents` دوباره محاسبه شود.
  - مانده قرارداد = `total_amount_cents − مجموع پرداخت‌های PAID` دوباره محاسبه/نمایش شود.
- اگر بعد از کاهش `total`، مجموع پرداخت‌ها از کل بیشتر شود: رفتار را تعریف کنید (مثلاً اجازه با مانده منفی/بستانکار، یا رد ویرایش تا اصلاح پرداخت‌ها). پیشنهاد پیش‌فرض: اجازه بستانکار (مشابه منطق فردی وقتی پرداخت بیش از قرارداد باشد).

### ۳.۳ کمیسیون / حقوق

- **فعلاً خارج از اسکوپ:** فقط دریافت پول.
- سهم مشاور، نقش‌ها، و accrual ماهانه برای قرارداد مدرسه پیاده نشود.

---

## ۴) پرداخت‌های قرارداد مدرسه

### ۴.۱ آیا الگوی اقساط نامنظم الان در سیستم هست؟

| قابلیت | وضعیت فعلی |
|--------|------------|
| چند پرداخت با مبلغ دلخواه + وضعیت PAID/PENDING | ✅ برای **دانش‌آموز فردی** |
| روش `INSTALLMENT` | ✅ فقط برچسب روش؛ منطق ویژه قسط ندارد |
| مانده = قرارداد − جمع پرداخت‌شده | ✅ برای Student |
| پرداخت متصل به مدرسه/قرارداد بدون `student_id` | ❌ وجود ندارد |
| نمایش سرانه `مبلغ ÷ تعداد` | ❌ وجود ندارد |

**نتیجه:** الگوی «فروردین ۸۰م، اردیبهشت ۲۰م، خرداد هیچ، تیر باقیمانده» از نظر مبلغ برای فرد پشتیبانی می‌شود؛ برای **مدرسه به‌عنوان طرف قرارداد** باید اضافه شود.

### ۴.۲ سناریوی مرجع

- قرارداد: مدرسه شهید بهشتی، ۴۰ نفر × ۱۰ میلیون = ۴۰۰ میلیون تومان
- فروردین: پرداخت ۸۰ میلیون → مانده ۳۲۰م → سرانه نمایشی `80/40 = 2` میلیون
- اردیبهشت: ۲۰ میلیون → مانده ۳۰۰م → سرانه `0.5` میلیون
- خرداد: بدون پرداخت
- تیر: پرداخت کل مانده (۳۰۰م) → مانده ۰ → سرانه `7.5` میلیون

الزام به از پیش ساختن قسط برای هر ماه **نیست**؛ فقط وقتی پول دریافت شد یک ردیف پرداخت ثبت می‌شود.

### ۴.۳ مدل پرداخت

- هر پرداخت یا به `student_id` وصل است (جریان فعلی) یا به `school_contract_id` (جدید) — یکی الزامی.
- فیلدها: مبلغ، وضعیت، روش، تاریخ سررسید/پرداخت، توضیحات، مرجع و …
- **سرانه:** `per_student_amount = payment.amount / contract.student_count`  
  - ترجیحاً محاسبه‌ای در API/UI (نه الزاماً ستون جدا، مگر برای audit).  
  - اگر مبلغ بر تعداد بخش‌پذیر نباشد: قانون گرد کردن مشخص شود (پیشنهاد: نمایش با اعشار تومان یا باقیمانده ریالی).

### ۴.۴ نمایش در بخش پرداخت‌ها

برای ردیف‌های مدرسه‌ای نشان داده شود:

- پرداخت‌کننده / عنوان: نام مدرسه (و در صورت نیاز برچسب «مدرسه‌ای»)
- مبلغ پرداخت‌شده در آن تراکنش
- تعداد دانش‌آموز قرارداد در زمان پرداخت (یا از قرارداد فعلی — ترجیح: snapshot تعداد روی پرداخت اگر ویرایش تعداد حساس است)
- معادل هر دانش‌آموز: `مبلغ ÷ تعداد`

فیلتر یا تفکیک بصری «فردی | مدرسه‌ای» در لیست پرداخت‌ها مفید است.

### ۴.۵ فرم ثبت پرداخت مدرسه‌ای

- انتخاب قرارداد مدرسه (نه انتخاب دانش‌آموز)
- مبلغ + تاریخ + وضعیت + روش
- پیش‌نمایش سرانه قبل از ثبت

---

## ۵) محدوده UI

| محل | تغییر |
|-----|--------|
| دانش‌آموزان — فرم ثبت/ویرایش | «نوع ثبت‌نام» = خصوصی/مدرسه‌ای؛ «نوع پرداخت» = مقادیر Billing فعلی؛ شاخه مدرسه‌ای = فیلدهای قرارداد |
| دانش‌آموزان — لیست | نمایش قراردادهای مدرسه (نام مدرسه، تعداد، مبلغ کل، مانده) یا تب/بخش جدا داخل همان صفحه |
| پرداخت‌ها | پشتیبانی ایجاد/نمایش پرداخت قرارداد مدرسه + سرانه |
| حقوق / کمیسیون مشاور برای مدرسه | فعلاً خیر |

## ۶) نیازمندی‌های بک‌اند (سطح بالا)

1. مدل + migration برای `SchoolContract` (و در صورت نیاز گسترش `Payment` با `school_contract_id` یا جدول پرداخت جدا).
2. API: CRUD قرارداد مدرسه (شامل ویرایش و محاسبه مجدد total/مانده).
3. API: ایجاد/ویرایش/حذف/لیست پرداخت‌های متصل به قرارداد؛ در پاسخ لیست: فیلدهای نمایشی مدرسه + `per_student_amount`.
4. اعتبارسنجی: `total = count × unit`؛ `student_count > 0`؛ برای مدرسه‌ای نام مدرسه اجباری.
5. عدم ایجاد `Student` هنگام ثبت قرارداد مدرسه‌ای.
6. فیلدهای جدید روی Student برای مسیر خصوصی: `registration_channel` (یا معادل)، `delivery_mode` (آنلاین/حضوری) — در صورت نگه داشتن دانش‌آموزان قدیمی، مقدار پیش‌فرض مناسب (مثلاً PRIVATE + migration داده).

---

## ۷) تصمیم‌های قطعی محصول (پاسخ ذی‌نفع)

1. **جای UI ثبت مدرسه:** داخل فرم دانش‌آموزان؛ با انتخاب نوع ثبت‌نام = مدرسه‌ای / خصوصی. فیلد Billing فعلی با عنوان **نوع پرداخت** جدا شود.
2. **کمیسیون/حقوق مدرسه:** فعلاً فقط دریافت پول.
3. **ویرایش تعداد و مبلغ واحد:** بله؛ total و مانده باید به‌روز شوند.

---

## ۸) خارج از اسکوپ فعلی

- ساخت خودکار N دانش‌آموز به ازای قرارداد
- تخصیص سهم پرداخت به دانش‌آموزان فردی
- کمیسیون مشاور و نقش‌ها روی قرارداد مدرسه
- الزام تقویم اقساط از پیش تعریف‌شده برای هر ماه

---

## ۹) معیار پذیرش (Acceptance)

1. در فرم، «نوع ثبت‌نام» فقط خصوصی/مدرسه‌ای است و «نوع پرداخت» جدا و با مقادیر قبلی کار می‌کند.
2. انتخاب خصوصی → الزام آنلاین/حضوری؛ ذخیره به‌صورت دانش‌آموز مثل قبل.
3. انتخاب مدرسه‌ای → نام مدرسه + تعداد + مبلغ واحد؛ نمایش مبلغ کل؛ ذخیره قرارداد بدون Student جدید.
4. چند پرداخت نامنظم روی یک قرارداد؛ مانده = کل − جمع PAID.
5. در پرداخت‌ها برای ردیف مدرسه: مبلغ کل پرداخت + معادل هر دانش‌آموز (`مبلغ/تعداد`).
6. ویرایش تعداد یا مبلغ واحد، total و مانده را درست به‌روز می‌کند.
