# مشخصات v2: دانش‌آموز خصوصی / مدرسه‌ای و قرارداد مدرسه

این سند **جایگزین فهم قبلی** در `school-contract-and-registration-types.md` است.  
مدل قبلی اشتباه بود: «نوع ثبت‌نام = مدرسه‌ای» را با **ساخت قرارداد مدرسه بدون دانش‌آموز** یکی گرفته بودیم. روال صحیح زیر است.

> **وضعیت پیاده‌سازی:** فیلدهای `registration_channel` و `school_contract_id` روی `Student`، API فیلتر، فرم‌های جدا «افزودن دانش‌آموز» / «افزودن مدرسه»، تب خصوصی vs مدارس با دراین‌داون دانش‌آموزان مدرسه، و پرداخت فقط روی قرارداد مدرسه — پیاده شده است.

---

## ۱) مشکل روال فعلی (چه چیزی اشتباه است)

الان تقریباً این‌طور کار می‌کند:

- در فرم ثبت دانش‌آموز، «نوع ثبت‌نام» به **مدرسه‌ای** تغییر می‌کند.
- همان فرم به‌جای ساخت دانش‌آموز، **قرارداد مدرسه** (`SchoolContract`) می‌سازد.
- پرداخت‌ها روی قرارداد مدرسه ثبت می‌شود (بدون `student_id`) — این بخش درست است.
- دانش‌آموزان واقعی مدرسه به‌عنوان `Student` لینک‌شده به همان قرارداد ثبت نمی‌شوند (یا مسیرشان با قرارداد مخلوط شده).

**هدف جدید:** قرارداد مدرسه و ثبت دانش‌آموز **دو عمل جدا** هستند؛ هر دانش‌آموز (خصوصی یا مدرسه‌ای) همیشه یک رکورد `Student` دارد.

---

## ۲) اصول محصول

| اصل | توضیح |
|-----|--------|
| هر دانش‌آموز یک `Student` است | چه خصوصی، چه مدرسه‌ای |
| نوع ثبت‌نام روی دانش‌آموز | `PRIVATE` یا `SCHOOL` — اجباری هنگام ثبت |
| قرارداد مدرسه موجودیت جداست | نام مدرسه، تعداد، اطلاعات پرداختی جمعی |
| پرداخت قرارداد مدرسه | فقط روی **مدرسه/قرارداد** (نه روی تک‌تک دانش‌آموزان) — مشابه پیاده‌سازی فعلی پرداخت `school_contract_id` |
| اطلاعات پرداخت فردی برای دانش‌آموز مدرسه‌ای | در فرم دانش‌آموز **لازم نیست**؛ قبلاً روی قرارداد مدرسه ثبت شده |

---

## ۳) ثبت دانش‌آموز

### ۳.۱ فیلد مشترک: نوع ثبت‌نام

| مقدار | معنی |
|--------|------|
| `PRIVATE` — خصوصی | دانش‌آموز فردی |
| `SCHOOL` — مدرسه‌ای | دانش‌آموز منتسب به یک مدرسه/قرارداد |

### ۳.۲ فیلدهای مشترک (خصوصی و مدرسه‌ای)

همه فیلدهای هویتی/عملیاتی فعلی ثبت دانش‌آموز خصوصی برای مدرسه‌ای هم لازم است، از جمله (نمونه، هم‌راستا با فرم فعلی):

- نام، نام خانوادگی، تماس، پایه/رشته، مشاور، وضعیت، …
- و هر فیلد دیگری که برای خصوصی اجباری/اختیاری است — مگر موارد استثنا در ۳.۳ و ۳.۴

### ۳.۳ خصوصی — اضافات

- **نحوه برگزاری:** آنلاین / حضوری  
  - UI: checkbox یا سوئیچ/سلکت واضح (آنلاین یا حضوری)
  - معادل دامنه: `delivery_mode = ONLINE | IN_PERSON`
- **نوع پرداخت / صورتحساب** (`enrollment_billing_mode` و مبالغ مرتبط) مثل جریان فعلی خصوصی باقی می‌ماند.
- پرداخت‌های این دانش‌آموز روی `student_id` ثبت می‌شود (جریان فعلی).

### ۳.۴ مدرسه‌ای — اضافات و حذف‌ها

**اضافه:**

- فیلد انتخاب/نام مدرسه — اتصال به قرارداد مدرسه موجود  
  - ترجیح دامنه: `school_contract_id` (انتخاب از لیست مدارس ثبت‌شده)  
  - اگر فقط متن آزاد بماند، بعداً به قرارداد وصل کردن سخت می‌شود؛ پیشنهاد محصول: **انتخاب از مدارس ثبت‌شده** (+ در صورت نیاز جستجو)

**حذف / مخفی از فرم دانش‌آموز مدرسه‌ای:**

- اطلاعات مربوط به **پرداخت و صورتحساب فردی** (مبلغ ثبت‌نام، نوع پرداخت ماهانه/تک‌جلسه/سالانه، اقساط دانش‌آموز و …)  
  - دلیل: این اطلاعات قبلاً در **ثبت مدرسه (قرارداد)** تکمیل شده است.

**نحوه برگزاری (آنلاین/حضوری):** برای مدرسه‌ای الزامی نیست مگر بعداً محصول بخواهد؛ پیش‌فرض این سند: فقط برای خصوصی.

## ۴) ثبت مدرسه (جدا از ثبت دانش‌آموز)

در **همان پنل دانش‌آموزان** دو اکشن جدا:

1. **افزودن دانش‌آموز**
2. **افزودن مدرسه** (کلید/دکمه مجزا)

### ۴.۱ فرم «افزودن مدرسه»

حداقل فیلدها:

| فیلد | توضیح |
|------|--------|
| نام مدرسه | اجباری |
| تعداد دانش‌آموزان | اجباری، عدد صحیح > 0 |
| اطلاعات پرداختی به‌ازای هر دانش‌آموز | مبلغ واحد (و در صورت نیاز بقیه فیلدهای قرارداد: کل = تعداد × واحد، وضعیت، توضیحات، …) |

مبلغ کل قرارداد = `تعداد × مبلغ واحد` (نمایش + اعتبارسنجی سرور).

این همان موجودیت `SchoolContract` است — **بدون** ساخت خودکار N دانش‌آموز.

### ۴.۲ ارتباط دانش‌آموز مدرسه‌ای با مدرسه

- بعد از ثبت مدرسه، هنگام «افزودن دانش‌آموز» با نوع = مدرسه‌ای، مدرسه انتخاب می‌شود.
- دانش‌آموزان واقعی یکی‌یکی (یا بعداً گروهی) ثبت و به همان قرارداد وصل می‌شوند.
- تعداد قرارداد (`student_count`) می‌تواند سقف توافقی باشد؛ نمایش «چند نفر از N ثبت شده» در UI مفید است (قوانین سخت‌گیرانه سقف در پیاده‌سازی تصمیم‌گیری شود).

---

## ۵) UI منوی دانش‌آموزان

بهترین شکل پیشنهادی: **دو بخش/تب واضح** در همان صفحه:

| بخش | محتوا |
|-----|--------|
| **خصوصی** | فقط دانش‌آموزان با نوع ثبت‌نام = خصوصی |
| **مدارس** | لیست مدارس/قراردادها (نام، تعداد توافقی، مبلغ کل، مانده، وضعیت، …) |

### ۵.۱ دراین‌داون مدرسه

- کلیک روی یک مدرسه → جزئیات مدرسه + **لیست دانش‌آموزان همان مدرسه**
- از جزئیات مدرسه بتوان دانش‌آموز جدید مدرسه‌ای برای همان مدرسه افزود (اختیاری ولی UX خوب)

### ۵.۲ دکمه‌های بالای صفحه

- در تب خصوصی: تاکید روی «افزودن دانش‌آموز» (نوع پیش‌فرض خصوصی)
- در تب مدارس: تاکید روی «افزودن مدرسه» + در جزئیات مدرسه «افزودن دانش‌آموز این مدرسه»

---

## ۶) پرداخت‌ها

| مسیر | رفتار |
|------|--------|
| دانش‌آموز خصوصی | پرداخت روی `student_id` — مثل الان |
| قرارداد مدرسه | پرداخت **فقط بر اساس مدرسه** (`school_contract_id`) — مثل پیاده‌سازی فعلی قرارداد؛ **نه** به‌ازای هر دانش‌آموز مدرسه‌ای |
| دانش‌آموز مدرسه‌ای | در لیست/فرم پرداخت‌ها به‌عنوان طرف پرداخت دیده نمی‌شود؛ پول مدرسه جداست |

نمایش پرداخت مدرسه‌ای:

- نام مدرسه
- مبلغ کل پرداخت
- در صورت نیاز: سرانه `مبلغ ÷ تعداد قرارداد` (snapshot تعداد روی پرداخت اگر ویرایش تعداد حساس است)
- مانده قرارداد = کل قرارداد − جمع پرداخت‌های PAID

کمیسیون / حقوق روی قرارداد مدرسه: فعلاً خارج از اسکوپ (فقط دریافت پول) مگر تصمیم بعدی.

---

## ۷) تأثیر روی بخش‌های مرتبط (باید هم‌راستا شوند)

| محل | تغییر لازم |
|-----|------------|
| فرم دانش‌آموز | نوع خصوصی/مدرسه‌ای؛ خصوصی → آنلاین/حضوری + پرداخت؛ مدرسه‌ای → انتخاب مدرسه، بدون فیلدهای پرداخت فردی |
| دکمه افزودن مدرسه | مجزا از افزودن دانش‌آموز |
| لیست دانش‌آموزان | تب/بخش خصوصی vs مدارس؛ کلیک مدرسه → دانش‌آموزان آن |
| API دانش‌آموز | فیلد نوع ثبت‌نام + لینک به `school_contract_id`؛ validation متفاوت خصوصی/مدرسه‌ای |
| قرارداد مدرسه | CRUD مستقل؛ دیگر از شاخه «نوع=مدرسه‌ای» داخل فرم دانش‌آموز ساخته نشود |
| پرداخت‌ها | مدرسه فقط از مسیر قرارداد؛ دانش‌آموز مدرسه‌ای payer نباشد |
| حقوق / خلاصه مشاوران | دانش‌آموزان مدرسه‌ای اگر به مشاور وصل‌اند در آمار دانش‌آموز می‌آیند؛ پول قرارداد مدرسه همچنان cash-only روی قرارداد است (طبق اسکوپ فعلی) |
| گزارش‌ها / داشبورد | تفکیک یا برچسب خصوصی vs مدرسه‌ای در صورت نمایش لیست دانش‌آموز |

## ۸) مدل دامنه پیشنهادی (سطح بالا)

```
SchoolContract
  - school_name, student_count, unit_price_cents, total_amount_cents, …
  - payments[] via school_contract_id

Student
  - registration_channel: PRIVATE | SCHOOL
  - if PRIVATE: delivery_mode ONLINE|IN_PERSON + enrollment billing fields + payments via student_id
  - if SCHOOL: school_contract_id (required); enrollment billing / individual payment fields not used
```

---

## ۹) معیار پذیرش

1. ثبت دانش‌آموز همیشه `Student` می‌سازد؛ نوع ثبت‌نام خصوصی یا مدرسه‌ای مشخص است.
2. خصوصی: آنلاین/حضوری + فیلدهای پرداخت مثل قبل.
3. مدرسه‌ای: انتخاب مدرسه؛ بدون ثبت اطلاعات پرداخت روی خود دانش‌آموز.
4. «افزودن مدرسه» جداست و نام + تعداد + اطلاعات پرداختی واحد/کل را می‌گیرد.
5. در منوی دانش‌آموزان: بخش خصوصی فقط افراد خصوصی؛ بخش مدارس فقط مدارس؛ کلیک مدرسه → دانش‌آموزان همان مدرسه.
6. پرداخت قرارداد فقط روی مدرسه است (نه دانش‌آموز مدرسه‌ای).
7. دیگر با انتخاب «مدرسه‌ای» در فرم دانش‌آموز، قرارداد مدرسه ساخته نمی‌شود.

---

## ۱۰) خارج از اسکوپ این نسخه (مگر درخواست بعدی)

- ساخت خودکار N دانش‌آموز هنگام ثبت مدرسه
- تخصیص خودکار مبلغ پرداخت مدرسه به دانش‌آموزان فردی
- کمیسیون مشاور/نقش‌ها روی قرارداد مدرسه
- تقویم اقساط ازپیش‌ساخته برای هر ماه

---

## ۱۱) وضعیت نسبت به سند قبلی

| موضوع | سند قبلی (اشتباه) | این سند (صحیح) |
|--------|-------------------|----------------|
| نوع ثبت‌نام = مدرسه‌ای | = ساخت قرارداد، بدون Student | = دانش‌آموز با لینک به مدرسه |
| محل ثبت قرارداد | داخل همان فرم دانش‌آموز با شاخه مدرسه‌ای | دکمه/فرم جدا «افزودن مدرسه» |
| دانش‌آموزان مدرسه | ساخته نمی‌شوند | ساخته می‌شوند و زیر مدرسه دیده می‌شوند |
| پرداخت مدرسه | روی قرارداد | روی قرارداد (بدون تغییر مفهومی) |
